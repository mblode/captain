## Steer in plain language

The usual way to drive Captain is the `/captain` skill from a Claude Code session. Ask for what you want and it runs the commands below:

> "fan out TIG-430 and TIG-431", "what's blocked", "show me the plans", "approve all the plans", "send 431 back: skip auth", "what's ready to merge"

You control three gates: approving each plan, answering questions, and the merge.

## Commands

```bash
captain start TIG-430 TIG-431         # Linear issues: one worktree + agent each
captain start "tidy the README"       # a free-form task, no Linear, current dir
captain start "tidy the README" --worktree            # the same, in its own worktree
captain "fix the flaky auth test" "tighten the CSP"   # several tasks: one worktree each
captain status                        # what's blocked, in flight, and ready
captain status --summary --since <t>  # what changed since that snapshot, one line each
captain approve tig-430               # or: captain approve all
captain approve tig-430 --note "low risk, scope matches"   # record why
captain reject tig-431 --note "don't touch auth"
captain gain                          # fleet telemetry, derived live (alias: audit)
captain triage tig-430 < plan.txt     # opt-in: sort one plan into clean / review before you read it
```

`captain --help` lists every command and flag. `captain start` routes on its arguments: a Linear issue id/URL fans out a worktree per issue; one free-form task runs in the current checkout (`--worktree` gives it a sibling worktree); several quoted free-form tasks fan out one worktree each, so you can hand Captain a decomposed objective without a tracker. Pass `--repo-path <path>` to pick the repo (a ticket's repo is decided per ticket, not by a static map); `--print` previews the brief without launching.

`captain status --summary` returns a snapshot token. Pass it back with `--since` and you get what changed since, one line per worktree ("tig-430: plan ready for approval", "tig-431: verified, ready to merge") plus a counts line, and the next token. The `/captain` driver ends every wake with that digest and when its next check is due.

## Triage before you read (opt-in)

`captain triage <ticket>` hands one plan, together with the worktree's definition of done, to a System One judge ([TypeSafe](https://typesafe.ai)'s Jev, a model that returns calibrated probabilities rather than prose) and asks six fixed questions: is the plan in scope, what is its blast radius, does it name the files, the work order and the proof tests, does it resolve an ambiguity silently. The card comes back `clean` (every answer decisive and safe) or `review` (anything else, with the reasons), plus a ready `captain approve … --note` line so the approval is recorded with its reasoning.

It is a triage, never a decision: nothing is approved, no gate is touched, and a missing or garbled answer is `review`. Set `TYPESAFE_API_KEY` to enable it; pipe the plan text on stdin or pass `--plan-file`. Without the key every other command works as before.

## The pipeline

Each agent's brief carries the whole software dev lifecycle and the agent self-drives it:

```text
plan, implement, /pr-reviewer, /tidy,
  "If the diff touches user-facing UI, run /product-design then /ui-design, …",
  "If the diff changes a rendered page or component, run /visual-qa before finishing.",
/pr-creator, /pr-babysitter, verifier verdict
```

`/pr-reviewer` runs before `/tidy` on purpose: the reviewer is read-only and writes a report whose fixes are committable, and `/tidy` applies that report's confirmed findings alongside its own sweep. Reversed, the report has nothing downstream to apply it.

The plan, implement, and verifier steps are fixed (`status` derives from them); the steps in between are configurable. Each one is either a `/skill` token or a plain-English instruction rendered verbatim — which is how a step becomes conditional, with no extra config schema. Set them in `~/.config/captain/config.json` (`.skills`) or with `CAPTAIN_SKILLS=/tidy,/pr-creator`.

Include `"$defaults"` to keep the built-in pipeline and add your own steps around it:

```json
{
  "skills": [
    "$defaults",
    "If the diff changes public API surface, run /dx-audit before opening the PR."
  ]
}
```

Without that token a non-empty list replaces the pipeline entirely. An empty or missing config falls back to the default chain above. `CAPTAIN_SKILLS` splits on commas, so prose steps containing a comma belong in the config file.

## How agents finish

Each worktree gets a definition of done (`.captain/rubric.md`, rendered from the Linear issue, no LLM call). The agent runs a fresh-context verifier sub-agent against it and writes `.captain/verdict.json` citing the rubric's hash: a valid pass shows READY TO MERGE with `✓ verified`, a fail shows NEEDS YOU with the verifier's summary. Verified learnings are saved per repo (`~/.claude/captain/memory/<repo>/learnings.md`) and fed into the next brief.

Every plan opens with a `## Decisions for the reviewer` section, at most five bullets, and that is what the driver's decision card quotes, so you read the sentences that matter rather than the plan. `captain gain` reports, per repo, how many tickets in a row cleared the plan gate first pass; when that streak is long and every pending plan in the repo is triage-clean and low risk, the driver may offer them as one approve-all decision instead of one each. It also reports each repo's fleet memory: how many inbox bullets no brief reads any more, how old the oldest is, and which traps two or more bullets name, so distilling the inbox into rules stops being a step nobody is prompted to take.

Captain keeps **no state**. `status`, `approve`, `reject`, and `gain` are all derived fresh on every call from cmux signals and the per-worktree `.captain/` files. There is no daemon to start, restart, or go stale.
