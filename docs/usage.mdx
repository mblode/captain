## Talk to the chat

Run `/captain` in a Claude Code session that stays open in its own cmux workspace. From your phone, use Claude Code Remote Control on that session.

> "rebuild billing settings, same behaviour as the old app", "pick up TIG-430", "what needs me?", "check the plans", "morning summary"

The chat turns each message into tasks, shows you one card with the harness and model it picked for each, and starts them on your yes. It wakes itself on a timer, moves work along, and only interrupts you for decisions.

## Commands

The chat runs these for you. They all take `--json`, and `--project <name>` when you have more than one project.

```bash
captain init rebuild --repo ~/code/app --wip 4   # a project: task folder + repo + WIP limit
captain add "rebuild billing settings"           # a task from a message
captain add TIG-430                              # a task from a Linear or Done Bear ticket
captain add "migrate users" --risk escalate      # plan approval before any code
captain start t-1 --harness codex --model gpt-6-luna --effort low
captain status                                   # the board
captain status --all-projects                    # every project's board, rows tagged by project
captain approve t-2 --note "scoped to one table" # release a plan
captain reject t-2 --note "reuse the invoices module"
captain send t-1 "use the existing date helper"  # steer a worker
captain peek t-1                                 # the end of its screen
captain review t-1                               # the other vendor reviews the PR
captain done t-1                                 # close it once merged (or: drop)
captain gain --since 7d                          # flow, decisions, cycle time
captain gain --all-projects --since 7d           # per project, plus a total
```

## Tasks

Each task is `~/captain/<project>/tasks/<id>.md`: frontmatter (`state`, `risk`, `harness`, `model`, `effort`, `blockedBy`, `branch`, `worktree`) and a markdown body that is the contract. Checklist lines (`- [ ] ...`) in the body become acceptance criteria. The project folder is its own git repo, so the task list has history.

`start` refuses a task whose `blockedBy` tasks aren't done, and refuses once the number of tasks in progress reaches the WIP limit. Every started task is a PR you'll review, so the limit is your review capacity, not the machine's. `--force` overrides both.

## The board

`captain status` is derived fresh on every call, from cmux (which workspace, busy or idle, a pending plan or question), GitHub (the PR and its CI), and the worktree's `.captain/` files. Nothing is stored, so there is no daemon to restart and nothing to go stale.

| Group | Meaning |
| --- | --- |
| NEEDS YOU | a plan to approve, a question, a failed verifier, or a PR with no CI |
| READY TO MERGE | CI green, the verifier passed, the other vendor's review passed |
| CAPTAIN'S MOVE | the chat has the next step: request a review, send back findings, restart a worker |
| WORKING | an agent is busy, CI is running, or a review is under way |
| QUEUED / BLOCKED | not started yet |
| MERGED | waiting for `captain done` |

## What a worker does

Each worker's brief carries the whole job, and the worker drives it:

```text
plan, implement, /tidy,
  "If the diff touches user-facing UI, run /product-design then /ui-design, ...",
  "If the diff changes a rendered page or component, run /ui-verification before finishing.",
/pr-creator, /pr-babysitter, verifier verdict
```

Escalate tasks start in plan mode and wait for `captain approve`. Other tasks write their plan to `.captain/plan.md` and carry on.

The steps between implement and the verdict are configurable in `~/.config/captain/config.json` (`.skills`), or with `CAPTAIN_SKILLS=/tidy,/pr-creator`. Include `"$defaults"` to keep the built-in steps and add your own:

```json
{
  "skills": [
    "$defaults",
    "If the diff changes public API surface, run /dx-audit before opening the PR."
  ],
  "harness": {
    "codex": { "model": "gpt-6-sol", "effort": "medium" },
    "cursor": { "bin": "cursor-agent" },
    "claude": { "model": "claude-sonnet-5", "effort": "high" }
  }
}
```

`.harness` sets each harness's binary, default model and effort. Codex defaults to `gpt-6-sol` at medium effort, and Cursor's binary defaults to `agent` (set `bin` to `cursor-agent` on an older install). A task's own `model` and `effort` win over it.

## How a task gets to ready

1. `start` writes a definition of done into the worktree (`.captain/rubric.md`, rendered from the task, no LLM call).
2. The worker runs a fresh-context verifier against it and writes `.captain/verdict.json`, citing the rubric's hash. Editing the rubric afterwards voids the verdict.
3. With CI green and a passing verdict, the chat runs `captain review`. A model from the other vendor (Codex for Claude's work, Claude for Codex's or Cursor's) reads the PR and writes `.captain/review.json`. It never edits code.
4. A failed review goes back to the worker. A passing one makes the task READY TO MERGE. You merge.

Workers append what they learned to `~/captain/<project>/learnings.md`, which is fed into every later brief.
